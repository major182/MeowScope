負荷がかかったときの速さと壊れにくさを確かめる（AC-17）。正しく動くかは、単体・結合・E2E で確かめる（テスト仕様書）。

## 1. 目的と合否の基準

| 要件 | 内容 | 確かめるテスト |
|---|---|---|
| NF-PF-01 | API の応答は、通常の操作で 95% が1秒以内 | PT-02・04・05 |
| NF-PF-03 | 同時に100人が使っても NF-PF-01 を満たす | PT-02・05 |
| NF-PF-04 | 差分同期は通常1分以内。5年分の記録があっても画面操作が遅くならない | PT-06・07 |
| NF-PF-02 | 起動からホームの表示まで3秒以内。記録の保存は0.5秒以内 | PT-07 |

- API：全体と操作ごとの p95 が 1秒未満、エラー率 1% 未満、確認（check）の成功 99% 超
- アプリ：3回の最大値で判定する。起動 3秒・保存 0.5秒・画面の操作 1秒・初めての全件の同期 60秒
- API の利用者とアプリの体感は、分けて判定する（件数の多い同期に、少ない操作の遅れが埋もれないように）

## 2. 道具

| 測るもの | 道具 | 置き場所 |
|---|---|---|
| API への負荷 | k6 2.3.0（Docker のイメージ `grafana/k6:2.3.0`）。スクリプトは TypeScript | `perf/src/` |
| アプリの操作 | integration_test を profile ビルドで `flutter run` する | `app/perf_test/` |
| 実行と後片付け | Node.js 24 で動く TypeScript（`perf/run.ts`） | `perf/` |
| サーバーと DB | `docker stats`、`pg_stat_activity`（接続数）、`pg_stat_statements`（遅い SQL） | 実行の道具が記録する |

- スクリプトの型チェックは CI で行う（`perf/` の `npm run typecheck`）
- このアプリはブラウザでは使わないので、ブラウザでの計測（Web Vitals）は行わない
- `flutter test` は debug ビルドでしか動かないので、アプリは profile ビルドで `flutter run` して、出力の `PERF_RESULT` の1行を受け取る。アプリの依存関係・ビルドの設定は変えない

## 3. 環境

- テストごとに、性能テスト専用の環境を立てる。`docker compose -p meowscope-perf` で、リポジトリの `compose.yaml` に `perf/compose.perf.yaml` を重ねる
- DB は PC に公開しない。サーバーは 8081 で受ける（Android のエミュレーターからは 10.0.2.2:8081）。開発用の環境（`meowscope`）とは、ボリュームもポートも別にする
- DB のパスワードと JWT の署名鍵は、実行のたびに作って環境変数で渡す（表示も保存もしない）。メールは送らない設定にする
- k6 は、専用の環境のネットワークの中からサーバーを呼ぶ

## 4. シナリオ

| ID | 種類 | 内容 | 時間 |
|---|---|---|---|
| PT-01 | smoke | 1人で全部の操作を一通り行う | 約1分 |
| PT-02 | load | 100人が同時に使う | 1分で増やし、10分続ける |
| PT-03 | stress | 100人から500人まで3分ごとに100人ずつ増やす。限界を探すので合否は付けない | 約15分 |
| PT-04 | spike | 10人から10秒で200人に増やして2分続け、10人に戻す | 約5分 |
| PT-05 | soak | 100人で60分続ける。遅くなっていかないか、メモリーが増え続けないかを見る | 約62分 |
| PT-06 | 大量データの同期 | 5年分のおうちを新しい端末で全件受け取る時間と、家族が10件記録した後の差分同期の時間を、3回ずつ | 約1分（準備を除く） |
| PT-07 | アプリ | 5年分のデータで、次の操作を3回ずつ。Windows で判定し、Android のエミュレーターは参考値<br>・起動からホームの表示<br>・記録の保存<br>・カレンダーを開く<br>・カレンダーの月の切り替え<br>・統計を開く<br>・体調のようすの日付の切り替え | 約5分（ビルドを除く） |

PT-02〜05 の1人の動きは、ログインして全件を受け取った後に、次の比率で1〜3秒おきに操作を繰り返す。

- 差分同期（受け取りだけ）：70%
- 記録を1〜3件送る同期：20%
- 写真つきの記録を送り、写真（300KB）を送って取得する：5%
- ログインのし直しか、トークンの更新：5%

アクセストークンの期限（15分）の前に、10分で更新する。

PT-07 のアプリの「起動」は、画面を作り直してからホームが出るまで。ファイルの DB の読み込みは含み、アプリのプロセスを立ち上げる時間は含まない。

## 5. テストデータ

| シナリオ | データ |
|---|---|
| PT-01〜05 | 100人。2人で1つのおうち（50のおうち）、猫は1〜3匹、30日分（1匹1日10件） |
| PT-06・07 | 1つのおうち、猫1匹、5年分（1日に約14件。体重は3日に1回、吐いたは20日に1回）。記録 26,249 件 |

- メールアドレスは `perf-<実行の印>-…@example.test` にして目印にする
- データは API で作る（PT-01〜06 は k6 の `setup`、PT-07 はテストの初め）

## 6. 実行の方法

```powershell
cd perf; npm ci                     # 初めのときだけ
node perf/run.ts smoke              # PT-01
node perf/run.ts load stress        # 名前を並べると順に行う
node perf/run.ts night              # PT-02〜07 をまとめて（約2時間15分）
node perf/run.ts load --short       # 時間を 1/10 にした動作の確認（合否・記録には使わない）
node perf/run.ts app-device         # PT-07 を USB でつないだ実機で（下の節）
node perf/run.ts load --keep        # 終わっても環境を捨てない。後から node perf/run.ts down
```

- PR や push では動かさない。動かしている間は、同じ PC でほかの重い処理をしない
- 開発用のサーバーは止めておく（`docker compose stop`。データは残る）
- 結果は `perf/results/<日時>_<ID>_<名前>/` に置く。コミットはしない
  - `env.txt`：コミット・マシン・開始と終了・結果
  - `summary.json`・`report.html`：k6 の集計と、グラフの報告
  - `stats.csv`：5秒ごとの CPU・メモリー・DB の接続数
  - `slow-sql.txt`：時間のかかった SQL の上位
  - `cleanup.txt`：後片付けの記録
  - `app-summary.txt`・`app.log`：アプリの計測

### Android の実機での計測

エミュレーターは PC の上で動くので、速さが実機と違う。NF-PF-02 の判定は、実機で測って行う。

1. 端末を再起動し、ほかのアプリを閉じ、十分に充電しておく
2. 端末の「開発者向けオプション」で、USB デバッグと「スリープモードにしない（充電中）」をオンにする
3. USB で PC につなぎ、デバッグを許可する（`adb devices` で見えること）
4. `node perf/run.ts app-device` を動かす。測っている間は端末に触らず、ケーブルを抜かない
   - 端末は `adb reverse` で、USB を通して PC の 8081 につなぐ（Wi-Fi の速さで揺れず、ファイアウォールの設定も要らない）
   - 端末が複数あるときは、環境変数 `PERF_DEVICE` で選ぶ
   - PT-07 の後に、いつものアプリを profile ビルドで入れ直し、プロセスを立ち上げる時間も含めた起動を `am start -W` の `TotalTime` で3回測る（最初の画面が出るまで。記録のみ）
5. 端末には、いつものアプリの profile ビルドが残る。使わないなら端末の設定から消す

PC の負荷が結果に影響するのは、サーバーを使う全件の同期だけ。画面の操作は端末の中で決まる。

## 7. 後片付け

- テストのたびに、成功・失敗・中断（Ctrl+C）のどれでも、専用の環境を `down -v` で丸ごと捨てる。開発用の DB には触れない
- 捨てる前に、目印の利用者と記録の件数を記録する
- 捨てた後に、専用の環境の volume とコンテナが 0 個であることを確かめて記録する

## 8. 記録

### 8.1 2026-11-11（コミット 4908915、PT-07 は e9efd2d）

環境：12th Gen Intel Core i5-12600K（16 スレッド）、メモリー 24GB、Windows 11、Docker Desktop。サーバーと DB は同じ PC。

API（PT-02〜06）は、時間の単位が ms。値は 中央値 / p95 / p99 / 最大 で、シナリオの中のリクエストだけを集計している。

| PT-02 load | 36,224 | 49.9 | 3 / 10 / 56 / 72 | 3 / 5 / 7 / 26 | 5 / 13 / 19 / 38 | 3 / 7 / 13 / 31 | 55 / 62 / 66 / 72 | 0% | 合格 |
| PT-03 stress | 131,812 | 140.5 | 3 / 11 / 57 / 1,670 | — | — | — | — | 0% | 記録のみ |
| PT-04 spike | 15,985 | 48.8 | 3 / 10 / 58 / 69 | 3 / 5 / 7 / 20 | 5 / 11 / 16 / 34 | 3 / 6 / 9 / 12 | 56 / 62 / 65 / 69 | 0% | 合格 |

|---|---|---|---|
| PT-06 | 中央値 495 / 最大 533 | 最大 5 | 合格 |

アプリ（PT-07、5年分。ms、3回）：

| 操作 | Windows（判定） | 基準 |
|---|---|---|
| 初めての全件の同期 | 29,427（2回の同期。下の注） | 60,000 |
| 起動からホームの表示 | 94・97・94 | 3,000 |
| 記録の保存 | 254・245・254 | 500 |
| カレンダーを開く | 416・416・417 | 1,000 |
| カレンダーの月の切り替え | 400・417・405 | 1,000 |
| 統計を開く | 415・399・393 | 1,000 |
| 体調のようすの日付の切り替え | 33・33・32 | 1,000 |

- 注：1回目の同期で受け取れたのは 24,987 件で、残りは2回目の同期（設定の「今すぐ同期」）で届いた。1回の同期で受け取る件数に上限があるため（#144）。また、同期の後に例外が出た（#145）
- Android のエミュレーター（参考値）は、2回とも途中で止まった。1回目は準備のデータを送る通信が切れ、2回目はエミュレーターが落ちた。実機で測った（8.2）
- 画面の操作の時間には、画面の切り替えの動き（約0.3秒）を含む

所見：

- 100人の同時利用でも、p95 は 10ms 前後で、NF-PF-01・03 を大きく下回った。500人（PT-03）でもエラーはなく、p95 は 11ms。サーバーの CPU は最大 95%（16 スレッドのうち約1つ分）。この PC では限界に届かなかった
- 急増（PT-04）でも、エラーや遅れの積み上がりはなかった
- 60分（PT-05）の間、p95 は変わらなかった。サーバーのメモリーは 394MB から 557MB へ少しずつ増えた。Java のヒープの上限（メモリーの 1/4）に届く前で、GC の前の増え方の可能性がある。本番の前に、より長い時間で確かめる
- 時間の合計が多い SQL は、記録の INSERT と、同期の排他（`pg_advisory_xact_lock`）。1回の平均は 0.2ms 以下

### 8.2 2026-11-11 Android の実機（コミット 84bf008 ＋ 統計の画面の測り方の手直し）

端末：ASUS Z01GD（Android 7.1.1、画面 1080×1920）。USB でつなぎ、サーバーと DB は 8.1 と同じ PC。PT-07 の 5年分（ms、3回）：

| 操作 | Android の実機（判定） | 基準 |
|---|---|---|
| 初めての全件の同期 | 50,081（1回の同期で 26,249 件すべて） | 60,000 |
| 起動からホームの表示 | 232・254・251 | 3,000 |
| 記録の保存 | 220・139・168 | 500 |
| カレンダーを開く | 663・699・696 | 1,000 |
| カレンダーの月の切り替え | 696・716・708 | 1,000 |
| 統計を開く | 709・670・669 | 1,000 |
| 体調のようすの日付の切り替え | 662・676・687 | 1,000 |
| プロセスからの起動（`am start` の TotalTime。記録のみ） | 407・363・346 | — |

- 判定：合格。#144 の修正（PR #147）の後なので、1回の同期で全件がそろった
- 統計を開く時間は、いちばん上の体重のグラフが出て画面が落ち着くまで（8.1 の Windows は体調のようすが出るまで）。画面の小さい端末では、体調のようすは画面の外にあり、スクロールするまで作られないため。体調のようすまでのスクロールは測らない
- プロセスからの起動（約0.4秒）に、画面を作り直してからホームが出るまで（約0.25秒）を足しても約0.65秒で、NF-PF-02 の3秒を大きく下回る

所見：

- 全件の同期は 50秒で、基準の 60秒に近い。古い端末（2017年ごろ）で5年分という重い条件だが、これより遅い端末や、記録がさらに多いおうちでは超えるおそれがある。超えても、同期は裏で続き、受け取った分から画面に出る
- 画面の操作は、どれも 0.7秒前後で基準の内。画面の切り替えの動き（約0.3秒）を含む
