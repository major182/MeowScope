サーバー（Spring Boot）と端末のログの決まりごと。エラーを追跡できることを目的とする（F-LG-01、F-LG-02）。

---

## 1. 方針

| 項目 | 内容 |
|---|---|
| 形式 | 1件を1行の JSON にする。開発のときだけ人が読みやすい形式にする |
| 出し先 | 標準出力だけ。集めるのは動かす環境の側（7章） |
| 重大度 | Alert〜Info の6段階（3章） |
| 作り方 | Spring Boot の構造化ログ（`logging.structured.format.console`）に、独自のフォーマッタを指定する |
| Datadog への備え | 今は使わないが、属性の名前を Datadog が設定なしで読める形にそろえ、将来そのまま送れるようにする |

## 2. JSON の属性

名前に「.」を含む属性は入れ子のオブジェクトにする（例：`usr.id` → `{"usr":{"id":"..."}}`）。値がないときは属性ごと出さない。

| 属性 | 内容 |
|---|---|
| `timestamp` | 出した時刻（ISO 8601、UTC） |
| `status` | 重大度 |
| `message` | 人が読むための文 |
| `service`、`env`、`version` | サービス、環境、アプリの版（Datadog の統合タグ） |
| `logger.name`、`logger.thread_name` | ログを出したクラス、スレッド |
| `request_id` | リクエストの ID |
| `usr.id` | 利用者の ID |
| `household.id` | おうちの ID（同期と、おうちの操作）。独自の属性 |
| `http.method`、`http.url_details.path`、`http.status_code` | アクセスログ |
| `duration` | 処理にかかった時間（ナノ秒） |
| `network.client.ip` | 利用者の IP |
| `evt.name`、`evt.outcome`、`evt.reason` | 出来事の種類、結果、理由 |
| `sync.received`、`sync.applied`、`sync.ignored`、`sync.rejected` | 同期の件数。独自の属性 |
| `error.kind`、`error.message`、`error.stack` | 例外 |

## 3. 重大度

| `status`（Datadog がそのまま読める値） | いつ使うか |
|---|---|
| `alert` | 直ちに対応する（乗っ取りの疑い） |
| `critical` | 主要な機能が止まっている（DB や写真の保存先に書けない） |
| `error` | 1つのリクエストが想定外の理由で失敗した |
| `warning` | 処理は続けたが、後で確かめる |
| `notice` | 正常だが、監査のために残す |
| `info` | 普段の動き |

SLF4J の重大度は ERROR・WARN・INFO の3つなので、`alert`・`critical` は ERROR に、`notice` は INFO にマーカー（`Severity.ALERT` など）を付けて表す。

## 4. リクエストの ID と問い合わせ番号

- `X-Request-Id` があれば検査して使い、なければ UUID を作る。英数字と `.` `_` `-` の64文字までだけを受け取る
- 応答のヘッダーとエラーの本文で返し、そのリクエストの間のログすべてに付ける
- 5xx のとき、画面に「問い合わせ番号」として表示する（F-LG-02）。4xx は利用者が直せる誤りなので表示しない
- 同期が失敗したときは、S-46 にも最後の問い合わせ番号を表示する
- アクセスログは1リクエストに1行、`info` で出す。`/actuator/health` は出さない

## 5. 出す出来事

| `status` | 出来事 | `evt.name` |
|---|---|---|
| `alert` | 使い終わった更新トークンが使われた | `refresh_token_reuse` |
| `critical` | 写真を保存先に書けない、DB に接続できない | - |
| `error` | 想定外の例外（500） | - |
| `warning` | 同期の変更を `rejected` にした、写真のファイルを消せない | `sync_rejected` |
| `notice` | ログインの失敗、パスワードの変更、退会、おうちを抜ける | `authentication`、`password_change`、`account_delete`、`household_leave` |
| `info` | ログインの成功、登録、ログアウト、招待の受諾、同期の完了 | `authentication`、`signup`、`logout`、`invitation_accept`、`sync` |

## 6. 出さない情報

公開リポジトリの CI にもログが出るので、次のものは出さない。テストで確かめる。

| 出さないもの | 代わりに出すもの |
|---|---|
| パスワード、トークン、`Authorization` ヘッダー、アプリパスワード | なし |
| メールアドレス | `usr.id` |
| 表示名、猫の名前、持病、メモ、記録の内容 | ID と件数 |
| 写真のファイルの内容 | 写真の ID |

## 7. 環境ごとの行き先

| 環境 | 形式 | 行き先 |
|---|---|---|
| 開発 | 人が読む形式 | ターミナル |
| テスト（CI） | JSON | GitHub Actions の実行ログ |
| AWS、PC | JSON | Docker のログ（`json-file`。10MB を5世代まで保持） |

CloudWatch Logs は使わない。AWS 固有の機能への依存を避け、費用も抑えるため（C-02、C-05）。調べるときは `docker compose logs` を使う。

Datadog を使うときは、Docker のログを Datadog Agent で集める。API キーは秘密の置き場に置き、文書とリポジトリには書かない。

## 8. 端末のログ

- 端末は、同期の失敗、例外、クラッシュを端末に記録し、同期のときに `POST /client-logs` でサーバーへ送る
- サーバーは受け取ったログを標準出力へ、`logger.name: client`、`status` を保ったまま JSON で出す。これでサーバーのログと同じ場所で追跡できる
- 端末の未送信のログは最新の1000件まで保持し、送信できたら消す。サーバーが停止していても端末の動作を妨げない
- 属性：`client.platform`（`windows` または `android`）、`client.app_version`、`client.os_version`、`client.occurred_at`、`client.request_id`（失敗した通信の問い合わせ番号）
- 利用者の ID は、端末の申告ではなくトークンから付ける
- 1回の送信は100件まで、本文は1件 2000 文字まで（8KB に収まる長さ）。回数は1時間に60回までとし、超えたら 429
- 端末から送れる重大度は critical・error・warning・notice・info（alert は送らせない）。属性は client.* と問い合わせ番号だけ
- 端末は、サーバーの応答があった同期の失敗（5xx は error、4xx は warning）、想定外の例外、画面の例外を記録する。つながらないだけの失敗は記録しない。例外は種類だけを書き、内容は書かない
- ログの保存（S-06）は、Windows は「ダウンロード」、Android はアプリの文書のフォルダーに置く。保存できないときのために、ログのコピーも用意する
- ログは信頼できない入力として扱う。改行と制御文字を取り除き、許可した属性だけを出力する
- 端末でも6章の出さない情報を守る。送信の前に、メールアドレスに見える文字列を伏せ字にする
- ログイン前の失敗はサーバーへ送れないので、S-06 でファイルに保存し、問い合わせ先へ添付してもらう
- 問い合わせ先のアドレスはビルド時に設定で渡し、リポジトリには書かない
- 一般公開のときは、手動の書き出しに頼れないので、クラッシュ収集サービス（Sentry など）を検討する
