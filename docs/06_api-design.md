## 1. 方針

- 形式は JSON の REST とし、パスは `/api/v1` から始める（NF-MT-03）
- 記録や猫などの共有データは、個別の API を作らず同期の API でまとめて送受信する。オフラインの処理と通信の経路を1つにするため
- 認証が必要な API は、`Authorization: Bearer <アクセストークン>` を付ける
- おうちの権限はサーバーで毎回確かめ、属していないおうちは 404 を返す（NF-SC-04）

## 2. 認証

アクセストークンは15分、更新トークンは30日で期限が切れる。更新のたびに新しい更新トークンへ交換し、使い回しを検知したら、そのユーザーの全トークンを無効にする。端末では OS の安全な保管場所に置く（NF-SC-07）。

| メソッド | パス | 説明 | 認証 |
|---|---|---|---|
| POST | `/auth/register` | 新規登録 | 不要 |
| POST | `/auth/login` | ログイン（回数制限あり：NF-SC-03） | 不要 |
| POST | `/auth/refresh` | トークンの更新 | 更新トークン |
| POST | `/auth/logout` | ログアウト | 必要 |
| POST | `/auth/password-reset/request` | 再設定の受付。確認コードをメールで送る | 不要 |
| POST | `/auth/password-reset/confirm` | 再設定の実行 | 不要 |

要求と応答：

| API | 要求の本文 | 応答 |
|---|---|---|
| `register` | `email`（半角、254文字まで）、`password`（半角、8〜64文字）、`displayName`（20文字まで） | 201。下の共通の形 |
| `login` | `email`、`password` | 200。下の共通の形 |
| `refresh` | `refreshToken` | 200。下の共通の形 |
| `logout` | `refreshToken` | 204 |
| `password-reset/request` | `email` | 202（登録の有無にかかわらず同じ） |
| `password-reset/confirm` | `email`、`code`（6桁の数字）、`newPassword`（新規登録と同じ決まり） | 200。下の共通の形（そのままログインした状態になる）。コードの誤り・期限切れ・使えなくなったときは 400（`INVALID_RESET_CODE`） |

```json
{ "accessToken": "JWT", "refreshToken": "ランダムな値", "expiresIn": 900,
  "user": { "id": "UUID", "email": "小文字のメールアドレス", "displayName": "はる" } }
```

- メールアドレスは小文字にそろえて保存し、大文字と小文字を区別しない。重複は 409
- ログインの失敗は、メールアドレスとパスワードのどちらの誤りかを返さない（どちらも 401）。同じメールアドレスで15分の間に5回失敗したら、15分の間 429 を返す（NF-SC-03）
- アクセストークンは HS256 で署名した JWT で、`sub` にユーザーの ID を入れる。署名鍵（32バイト以上）は秘密の置き場に置き、環境変数 `JWT_SECRET` で渡す

パスワードの再設定（F-AU-03）：

- メールに6桁の確認コードを送る。Windows と Android で同じ操作になり、メールを別の端末で読んでも使える
- 登録されていないメールアドレスでも 202 を返し、メールは送らない（登録の有無を知られないため）。メールを送れなかったときも 202 にして、サーバーのログに error を残す
- コードは DB にハッシュだけを置く。15分で期限が切れ、5回間違えたら使えなくなる。送り直すと前のコードは使えなくなる。送り直しは1分あける（1分以内の受付ではメールを送らない）
- 変えたら、ほかの端末のログイン（更新トークン）はすべて無効にし、この端末にトークンを渡す
- メールは SMTP で送り、送り先のサービスは設定（環境変数 `MAIL_*`）だけで切り替える（Q-26）。設定がなければ送らずに warning を残す
- ログには、メールアドレスとコードを出さない

ログアウトの動作：

- 同期済みのデータは端末から消す
- 未送信の記録と写真は、ユーザーの ID を付けて端末に残し、同じユーザーが再ログインしたら送信する
- 別のユーザーのログイン中は、残したデータを表示も送信もしない
- 更新トークンの期限が切れても、端末での記録は続けられる。再ログインの後に送信する

## 3. アカウント

| メソッド | パス | 説明 |
|---|---|---|
| GET | `/me` | 自分の情報（メールアドレスを含む） |
| PATCH | `/me` | 表示名の変更 |
| PUT | `/me/password` | パスワードの変更 |
| PUT | `/me/icon` | アイコンの登録 |
| GET | `/users/{id}/icon` | ユーザーのアイコンの取得。自分か、同じおうちのメンバーだけ |
| DELETE | `/me` | 退会。本文に `keepRecords` |

- `PUT /me/password` は `currentPassword` と `newPassword`（新規登録と同じ決まり）を受け取る。今のパスワードが違えば 403。変えると全端末の更新トークンを無効にし、新しいトークンの組を返す
- `DELETE /me` は属するおうちをすべて抜けて（下の「抜ける」と同じ）から、ユーザーを物理削除する。204

## 4. おうち

| メソッド | パス | 説明 |
|---|---|---|
| POST | `/households` | おうちの作成。端末が作ったおうちの ID と名前、標準の8項目（ID を含む）を受け取って登録し、作った人をメンバーにする。サーバーでは標準の項目を作らない。記録項目の ID がほかのおうちの項目とぶつかったら 409 で、おうちも作らない。入力の誤りは 400 |
| POST | `/households/{id}/invitations` | 招待のリンクの作成。メンバーだけ（ほかは 404）。応答は `token`・`link`（`meowscope://invite?token=...`）・`expiresAt` |
| POST | `/invitations/accept` | 招待の受諾。本文は `token`。応答は `householdId`。知らない・期限切れ・使用済みはどれも 404。すでにメンバーの人が受けても使用済みにしない |
| POST | `/households/{id}/leave` | おうちを抜ける。本文に `keepRecords` |

招待のリンクは作ってから60分、1回だけ使える。トークンは推測できないランダムな値で、DB にはハッシュだけを置き、ログにも出さない。メールでの招待はしない。

`POST /households/{id}/leave` は `keepRecords`（必須）を受け取り、`{"householdDeleted": 真偽}` を返す。最後の1人なら、おうちと中のデータをすべて消す。属していなければ 404。端末は成功の後に、そのおうちのデータを消す。

おうちの作成の要求は `{"id": "UUID", "name": "みけ家", "recordTypes": [{"id", "name", "icon", "kind", "sortOrder"}]}`。新しく作ったら 201、自分のおうちとして登録済みなら 200（送り直し）、他の人のおうちの ID なら 404 を返す。端末は同期待ちに「作成」を残し、同期の最初に送る。

## 5. 同期

```text
POST /sync
```

端末の変更を送り、続けて相手の変更を受け取る処理を、1回の通信で行う。
端末は、同期待ちの行の「送る時点の内容」を丸ごと送る。同じ行を何度変えても、送るのは最後の内容だけになる。

要求：

```json
{
  "lastSeq": 1200,
  "changes": [
    {
      "table": "records",
      "id": "UUID",
      "updatedAt": "2026-11-02T00:10:00Z",
      "deletedAt": null,
      "data": { "catId": "UUID", "recordTypeId": "UUID" }
    }
  ]
}
```

応答：

```json
{
  "results": [
    { "id": "UUID", "status": "applied", "reason": null, "field": null },
    { "id": "UUID", "status": "rejected", "reason": "invalid", "field": "level" }
  ],
  "changes": [],
  "nextSeq": 1215,
  "hasMore": false,
  "fullResyncRequired": false
}
```

| 項目 | 動作 |
|---|---|
| 競合 | サーバーが後から受け取った変更を採用する（BR-10）。受け取った順に `server_seq` を振る。番号は確定の順に振り、読むときは確定を待つので、小さい番号の行を後から取りこぼすことはない（DB 設計書 2章）。`updatedAt` は比べない（表示のためだけに保存する） |
| 結果の値 | `applied`（反映）、`ignored`（今の内容と同じ。再送など。番号は進めない）、`rejected`（権限や内容の誤り） |
| 受け付けない理由 | `rejected` のときだけ `reason` を返す。値の誤りのときは、どの項目かを `field` で返す。`unknown_table`（知らない表。アプリとサーバーの版のずれ）、`forbidden`（自分のおうちではない）、`not_found`（参照する猫・項目・記録がない。ほかのおうちの猫・項目なら `forbidden`）、`invalid`（値が決まりに合わない）、`too_many`（写真3枚・ボタン4つの上限超え）、`constraint`（DB の制約に反した）。端末は、理由が空で届いたときは `unknown` として残す |
| 反映の順 | 1回の要求の中では、おうち → 猫・記録項目 → 記録・ウィジェットのボタン・お薬の予定 → 写真の情報 → 設定 の順に反映する。1件が `rejected` でも、ほかは反映する |
| 権限 | 行のおうちと変更の後のおうちの両方が、自分の属するおうちであること。おうちの付け替えは `rejected`。記録の投稿者の ID は、端末の申告ではなくトークンのユーザーにする |
| 再送 | 同じ変更を再送しても結果は同じになる。通信が切れても安全に送り直せる |
| 分割 | 1回で送受信するのは500件まで。`hasMore` が真なら続けて呼ぶ。`nextSeq` は、続きがあれば返した最後の変更の番号、最後のページならサーバーの最新の番号 |
| 全件の取り直し | `lastSeq` がサーバーの最新の番号より先のとき（サーバーの DB を作り直した）と、前回の同期の後に自分が別のおうちに加わったときは `fullResyncRequired` を返す。端末は `lastSeq` を 0 にして呼び直す。削除から90日を過ぎた行や、最後の1人が抜けたおうちを完全に消す前の位置から同期してきたときも同じ（DB 設計書 7章）。端末は全件を取り直し終えたら、受け取らなかった行（サーバーから受け取ったことがあり、送っていない変更がなく、その同期で送ってもいない行）を消す。途中で止まったら消さない |
| 受け取る変更 | 各変更は `table`・`id`・`seq`・`updatedAt`・`deletedAt`・`data` を持つ。端末は、同期の最中にできた変更がある行には反映しない |
| 同時実行 | 端末では同時に1つだけ実行する |

`rejected` の変更は自動では再送しない。端末は、どの行がなぜ送れなかったかを残し、S-48 で利用者に原因と対応を示す（利用者が「送り直す」を選べば再送する）。

同期する表と `data` に入れる主な列は次のとおり（列の意味は [05 DB 設計書](05_db-design.md)）。おうちそのものの作成は `POST /households` で行う。

| 表 | `data` の主な列 |
|---|---|
| `households` | `name` |
| `cats` | `householdId`、`name`、`birthDate`、`sex`、`conditions`、`status`、`anomalyThresholds`（しきい値。DB 設計書の形）。受け取るときは `hasIcon`（アイコンの有無）も入る |
| `record_types` | `householdId`、`name`、`icon`、`kind`、`sortOrder`、`hidden`（非表示） |
| `records` | `catId`、`recordTypeId`、`recordedAt`、`authorName`、`valueNumber`、`level`、`detail`、`memo`。受け取るときは `authorId`（投稿者の ID。退会した人なら空）も入る |
| `record_photos` | `recordId`、`sortOrder`（1〜3）。受け取るときは `sizeBytes` と `uploaded`（画像が送られたか）も入る。画像の本体は 6章の API で送受信する |
| `user_settings` | `weekStart`、`reminderHours`（1〜48、空はオフ）、`notifications`（種類ごとのオン・オフ）、`anomalyMethod`（`statistical` か `threshold`）。`id` は見ず、自分の行を更新する |
| `medication_schedules` | `householdId`、`catId`、`name`（20文字まで）、`dose`（20文字まで）、`timeOfDay`（`HH:mm`、00:00〜23:59）、`enabled`（送らなければオン）。猫は同じおうちのものであること |
| `widget_buttons` | `recordTypeId`、`sortOrder`（0〜3）。持ち主はトークンのユーザーで、自分の分だけを送受信する。1人4つまで（超えたら `rejected`）。記録項目は自分の属するおうちのものであること |
| `household_members`（受け取りのみ） | `householdId`、`userId`、`displayName` |
| `users`（受け取りのみ） | `displayName`、`hasIcon`。同じおうちのメンバーだけ。メールアドレスは送らない |

退会やおうちを抜ける操作を別の端末で行ったときは、次の同期で検知し、端末のそのおうちのデータを消して S-04 へ戻る。

## 6. 写真

| メソッド | パス | 説明 |
|---|---|---|
| PUT | `/photos/{id}` | 写真の送信。画像のみ、上限 5MB（NF-SC-08） |
| GET | `/photos/{id}` | 写真の取得 |
| PUT | `/cats/{id}/icon` | 猫のアイコンの登録 |
| GET | `/cats/{id}/icon` | 猫のアイコンの取得 |

写真の情報（`record_photos`：`recordId`、`sortOrder`。受け取りでは `sizeBytes` と送られたかの `uploaded` も）は同期で送り、その後で画像を送る。写真の取得もおうちの権限を確かめ、自分のおうちでなければ 404 を返す。

- 送信の本文は画像そのもの（`Content-Type` は `image/jpeg`・`image/png`・`image/webp`）。形式はファイルの先頭の印でも確かめ、違えば 415。5MB を超えたら 413
- 1つの記録に3枚まで。4枚目の写真の情報は `rejected`
- 写真の情報に削除の印が付いたら、サーバーの画像のファイルも消す
- アイコンは本文が画像そのもので、上限 1MB（端末は 512px に縮める）。保存したら行の通し番号を進め、同期の `users`・`cats` の `hasIcon` で相手に届ける。権限がなければ 404
- 端末は送る前に長辺 1600px の JPEG に縮め、撮影場所などの情報（EXIF）を外す

## 9. エラーの形式

RFC 9457（Problem Details）の形式で返す。

```json
{
  "type": "about:blank",
  "title": "入力内容に誤りがあります",
  "status": 400,
  "code": "VALIDATION_ERROR",
  "requestId": "問い合わせ番号"
}
```

| 状態コード | `code` | `title` | 使う場面 |
|---|---|---|---|
| 400 | `VALIDATION_ERROR` | 入力内容に誤りがあります | 入力の誤り |
| 400 | `INVALID_RESET_CODE` | 確認コードが違うか、期限が切れています | 確認コードの誤り（同じ 400 なので `code` で見分ける） |
| 401 | `UNAUTHORIZED` | ログインが必要です | 未認証、トークンの期限切れ |
| 403 | `FORBIDDEN` | この操作は許可されていません | 許可されていない操作 |
| 404 | `NOT_FOUND` | 見つかりません | 存在しない、または属していないおうち |
| 405 | `METHOD_NOT_ALLOWED` | この方法では呼び出せません | パスに合わないメソッド |
| 409 | `CONFLICT` | すでに登録されています | メールアドレスの重複、記録項目の ID の重複 |
| 413 | `PAYLOAD_TOO_LARGE` | 容量が大きすぎます | 写真・アイコンの容量超過 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | この形式には対応していません | 画像として読めない写真・アイコン |
| 429 | `TOO_MANY_REQUESTS` | 回数の上限に達しました。しばらく待ってからやり直してください | 回数制限 |
| 500 | `INTERNAL_ERROR` | サーバーで問題が発生しました | サーバーの異常。`requestId` を画面に表示する（F-LG-02） |

`title` は人が読むための文で、アプリは `code` を見て画面の文を決める。表にない状態コードは、4xx なら `VALIDATION_ERROR`、5xx なら `INTERNAL_ERROR` にする。

## 10. アプリの更新（Ver.1.1）

| メソッド | パス | 説明 |
|---|---|---|
| GET | `/app-releases/{platform}/latest` | いちばん新しい版の情報。`platform` は `android`・`windows` |
| GET | `/app-releases/{platform}/file` | いちばん新しい版のファイル（Android は APK、Windows はインストーラー） |

- どちらも認証が必要（ログインしていない間は確かめない）。サーバーの URL が入ったファイルを、利用者だけに配るため
- 版の情報の本文：`{"version": "1.0.1", "buildNumber": 2, "sha256": "<64 文字>", "sizeBytes": 76346880}`。端末は `buildNumber` が自分より大きいときだけ知らせる（要件定義書 BR-34）
- 置いてある版がない、または `platform` が違うときは 404（`not_found`）
- ファイルは `Content-Type: application/octet-stream` で返す。端末は受け取った後に SHA-256 を計算し、版の情報の `sha256` と一致したときだけ入れる（BR-33）
- サーバーは、決まったフォルダー（`RELEASES_DIR`。既定 `/data/releases`）の `<platform>/release.json`（版の情報）とファイルを読むだけ。置き方はデプロイ設計書 6.4
